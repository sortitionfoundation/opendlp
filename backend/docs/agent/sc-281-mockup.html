sc-281 Stratified selection improvements · Epic 426

Implement recommended target changes with one click

When an initial selection can't meet its targets, the algorithm already tells the organiser exactly which minimum or maximum to relax. Today they have to copy those numbers in by hand. This change adds Accept buttons that apply a recommendation — and optionally re-run the selection — in a single action.

type Feature priority High pattern from sc-447 replacements surface Targets “Check” page
01

The problem

On the targets page, hitting Check runs a feasibility check. When the quotas can't all be met, the page already shows structured suggestions — “Suggested minimum: 12 (currently 15)”. But they're read-only prose: to act on one, the organiser must open edit mode, find the value, and retype the number. The replacement flow (sc-447) solved the identical problem with one-click accept buttons; this brings that to the initial selection.

What exists today. check_targets_detailed() produces a TargetAnnotation(level="suggestion", suggested_value=N) for every min/max the solver would relax, keyed to its category & value. The template renders them — with no way to apply them.

What we add. An Accept button on each suggestion, plus page-level Accept all and Accept all & re-run selection. Each posts to a new route that applies the authoritative suggested value via the existing target-save service, then re-checks or runs.

03

User flow

The happy path from an infeasible check to a feasible, running selection — all without leaving the targets page.

STEP 1

Check targets

Organiser runs the feasibility check; quotas are infeasible.

STEP 2

See suggestions

Each unmeetable min/max shows a suggested value, inline with its row.

STEP 3

Accept

One suggestion, or Accept all. Server applies & saves the real targets.

STEP 4a

Re-check

Page reloads with a fresh check — the accepted suggestion is gone.

STEP 4b

…& re-run

Or go straight to a live selection run from the same click.

04

Data flow

Server-side and authoritative: the new route re-derives the suggestions itself rather than trusting posted numbers, applies each through the existing target-value service, then redirects to either a re-check or a selection run. No new domain logic, no client-side state.

request / apply re-check branch re-run branch reused, unchanged
05

Scope & decisions

Surface

Targets Check page. It already holds the structured suggestions; a failed run only stores plain-text error, so this is the only place with the data.

Granularity

Per-suggestion Accept + Accept all, mirroring the replacement feature exactly.

Action

Accept applies + saves + re-checks. A separate Accept all & re-run applies, saves, and starts the selection.

In scope

  • One-click accept of a recommended min or max, server-side.
  • Accept-all and accept-all-and-run page actions.
  • Re-check after accepting so feasibility is confirmed.

Out of scope

  • Side-by-side “review in context” edit page.
  • Anything replacement-specific (original targets, saved-number handling).
  • Changing how suggestions are computed — reused as-is.
06

One new route and two template edits. The heavy lifting — feasibility and persistence — is entirely reused.
