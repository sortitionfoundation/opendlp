I asked Claude about avoiding drift/contract style testing. Full response:

## The concrete version of the problem

Say you have:

```python
@app.get("/api/widgets/<int:id>")
def get_widget(id):
    w = Widget.query.get_or_404(id)
    return {"id": w.id, "name": w.name, "price_pence": w.price_pence}
```

and a vitest test:

```javascript
const WIDGET = { id: 42, name: "Sprocket", price_pence: 1250 }; // hand-typed fixture
test("formats price", () => {
  expect(formatPrice(WIDGET)).toBe("£12.50");
});
```

Someone renames `price_pence` → `price_minor_units`. Pytest passes (it was updated). Vitest passes (it never knew). Production breaks.

The root cause is that there are **two independent copies of the truth**. Every solution below is really answering one question: _where does the single copy live, and what CI check proves both sides still agree with it?_

---

## 1. Golden fixtures generated by the Python test suite

Your pytest suite hits each endpoint and writes the real response to `fixtures/api/widget.json`. Vitest imports that same file rather than a hand-typed literal.

```python
def test_widget_fixture(client, snapshot_dir):
    resp = client.get("/api/widgets/42")
    write_fixture(snapshot_dir / "widget.json", resp.get_json())

```

```
import widget from "../fixtures/api/widget.json";

```

CI runs pytest, then `git diff --exit-code fixtures/` — a stale fixture fails the build; a changed fixture fails vitest if the JS wasn't updated too.

- **Pros:** trivially simple, no schema language, no new dependencies. The fixture is _real output_, so it catches renames, type changes, nesting changes — everything. Reviewers see the API change as a diff in the PR, which is genuinely valuable.

- **Cons:** you must normalise volatile fields (timestamps, UUIDs, ordering) or you'll get spurious diffs. It pins one _example_, not the _contract_ — it won't tell you a field is optional, or that `name` can be null. Coverage is only as good as the scenarios you remember to capture.

This is usually the highest value-per-hour option for a small app, and it composes with everything below.

## 2. Hand-written JSON Schema, shared by both sides

Keep `schemas/widget.json` in the repo. Python asserts responses conform (`jsonschema`); JS asserts fixtures conform (`ajv`).

```python
validate(instance=resp.get_json(), schema=load("widget.json"))
```

```javascript
const validate = new Ajv().compile(schema);
test("fixture matches contract", () => expect(validate(widget)).toBe(true));
```

- **Pros:** language-neutral, mature validators on both sides, expresses optionality/nullability/enums properly. Cheap to adopt incrementally — one endpoint at a time.

- **Cons:** the schema is a third hand-maintained artefact, so it can itself drift _unless_ you set `additionalProperties: false` and require it in Python tests. Doesn't cover routes, methods or status codes.

## 3. OpenAPI as the single source of truth (spec-first)

One `openapi.yaml` describing paths, methods, and response bodies. Python side: `connexion` (routes _from_ the spec) or `openapi-core`/`schemathesis` to validate responses in tests. JS side: dereference the spec and validate fixtures with ajv.

- **Pros:** covers the whole surface, not just body shapes. Free documentation, mock servers, client generation. `schemathesis` will even property-test your endpoints against the spec, which finds cases you didn't think to write.

- **Cons:** YAML maintenance overhead that's disproportionate for "a few JSON endpoints". Spec-first requires discipline: it only helps if response validation is _enforced_ in tests, otherwise the spec quietly becomes fiction.

## 4. OpenAPI generated from Flask (code-first), committed and diff-checked

`flask-smorest`, `spectree` or `flask-pydantic-spec` derive the spec from your marshmallow/Pydantic response schemas. A CI step regenerates `openapi.json` and fails on a non-empty diff; JS validates fixtures against the committed file.

- **Pros:** no duplication — the spec follows the code automatically. The generated file in the diff makes API changes visible in review. Bonus: adopting response serialisers usually improves the endpoints anyway.

- **Cons:** it documents what you _declared_, not what the handler actually returned, unless you also enable response validation. Requires restructuring endpoints around schemas. Generator quirks mean diffs can churn on library upgrades.

## 5. Types as the source of truth: Pydantic → JSON Schema → JS

Define response models in Pydantic, return them from the endpoint, then export `Model.model_json_schema()` at build time. Optionally run `json-schema-to-typescript` and consume the types from vanilla JS via JSDoc + `checkJs`.

- **Pros:** truth lives where the data is constructed, so it's very hard to bypass. Runtime enforcement in Python plus static checking in the editor for JS.

- **Cons:** types are erased at runtime in JS, so you still want ajv for the fixtures themselves. Build-step complexity. Some refactoring of existing endpoints.

## 6. Consumer-driven contracts (Pact)

Vitest declares "when I GET /api/widgets/42 I expect a body matching X"; that emits a pact file; `pact-python` replays it against the real Flask app and verifies.

- **Pros:** genuinely bidirectional — it fails when the provider drops a field the consumer actually uses, and _doesn't_ fail for fields nobody consumes. The most rigorous option.

- **Cons:** heavyweight for a monolith with one consumer. Broker infrastructure, a real learning curve, and `pact-python`'s ergonomics lag the JS side. Best justified when frontend and backend deploy independently.

## 7. Integration tests against a live server

Boot Flask in CI and drive the JS against it (Playwright, or node-side fetch tests).

- **Pros:** the only approach that verifies the actual wire behaviour including headers, status codes and content negotiation.

- **Cons:** slow, flaky, needs fixture data and a running database. Crucially, it doesn't guard your _unit_ test fixtures at all — those can still drift while the e2e suite passes.

---

## What I'd suggest

For "a Flask app with a few JSON endpoints", start with **1 + 2**: generated golden fixtures, plus a JSON Schema with `additionalProperties: false` validated on both sides. That gives you concrete data for the JS tests and a real contract for the shape, with about a day's work and no new frameworks.

Reach for **4** when the number of endpoints grows past the point where hand-written schemas are pleasant, and for **6** only if the frontend and backend start shipping on separate cadences.

The invariant to protect, whichever route you take: **vitest must never contain a hand-typed literal of an API response**. The moment it does, you have a second copy of the truth again.
