Workflow: where respondents and targets live

Every assembly has one home for its respondents and targets: either an external Google Sheets spreadsheet, or the OpenDLP database. This page follows the data from where it starts to where the selection reads it, and back out again.

One source of truth per assembly. With Google Sheets, the spreadsheet is the truth and OpenDLP keeps nothing on disk. With the OpenDLP database, the database is the truth: copies can exist elsewhere (a CSV you uploaded, a spreadsheet OpenDLP exports to) but they are secondary, and changing them does not change the assembly.

Path 0 — External Google Sheets

The respondents and targets live in a Google Sheets spreadsheet that the organiser looks after. OpenDLP is told the spreadsheet's URL and the names of the two tabs that hold the respondents and the targets. It never stores the respondents: it reads them into memory when a selection runs, and writes the results straight back to the same spreadsheet.

Telling OpenDLP about the spreadsheet

On the Data tab the organiser picks Google Sheets, pastes the spreadsheet URL, and names the tab with the respondents and the tab with the targets. For a replacement selection there can also be a third tab, listing the people already selected. The spreadsheet must be shared with OpenDLP's service account so it can read and write.

Everything about the data — adding a respondent, changing a target value, fixing a typo — happens in the spreadsheet, using whatever tools the organiser already has. OpenDLP only sees the change the next time it reads.

Nothing about respondents is saved to disk

When a selection runs, OpenDLP reads both tabs into memory, runs the selection, and writes the selected respondents (and the remaining respondents) to new tabs in the same spreadsheet. The tab names come from the sortition-algorithms library (GSheetTabNamer), not from OpenDLP: Original Selected - output - N and Remaining - output - N, where N is the lowest number not already used, so earlier runs are never overwritten. None of the respondent details are saved by OpenDLP; once the task is done they are gone from OpenDLP entirely.

That makes this path simple to reason about for erasure requests: the spreadsheet is the only copy to blank.

Targets: enter them in the web UI, from scratch

Add each target (Gender, Age ...), then its values (Woman, Man, Non-binary ...), then the numbers: percentage, and the min and max to select. See the targets and fields workflow for that flow in detail.

Targets: build them from respondent data

When respondents are already in the database, OpenDLP can propose targets and values from the respondents' columns: pick a column, and its distinct values become the target's values. The organiser then fills in the numbers in the web UI. This is the only route that needs respondents first.

Targets: upload a targets CSV

One row per target value: the target, the value, and the numbers. The planned imports from Google Sheets, xlsx files, Excel Online and so on take a table of the same shape, so on this page they count as variations of the CSV upload.

Targets: copy from another assembly (planned)

Copies the targets, their values and each value's percentage, but not the min and max. Those are worked out afresh from the copied percentage and the new assembly's number to select — the old assembly's min and max were for a different number of people.

Respondents: upload a respondents CSV

One row per respondent, one column per question. As with targets, the planned imports from other tabular sources take a table of the same shape and count as variations of this upload.

Respondents: the registration page

The organiser builds a registration page, and each person who signs up becomes a respondent in the database. Targets are expected to exist before the page is built: building the page starts by linking each target to the question that answers it, so that every respondent arrives with the data every target needs. See the registration page workflow.

Around the paths

Combining routes

The paths are the common journeys, not the only ones. Any route into the database can be followed by any other, because they all write to the same place:

  • Upload a targets CSV, then edit it in the web UI: change values, adjust numbers, add a whole new target.
  • Build targets from respondent data, then add a target the data does not cover yet.
  • Run a registration page and upload extra respondents (path 4) while also auto-exporting to Google Sheets (path 3).

The one ordering that matters: a registration page is built from targets, so targets come before the page. Adding a target after the page is live means the page needs a question for it too.

Selection from the database

The selection reads targets and respondents from the database and records the result there too: each respondent's status changes to show whether they were selected. Nothing needs to go out to a spreadsheet for the selection to happen; exporting the result is an optional extra.

Exports: secondary copies

Exports are not part of how data gets in, but they help teams with tasks that suit a spreadsheet better than a web page.

In every case OpenDLP stays the source of truth. A change made in an exported copy does not flow back, and the next auto-export will overwrite it.

Planned and possible routes not drawn as paths

Planned:

  • Import a table of targets or of respondents from Google Sheets, an xlsx file, Excel Online and so on. Same shape as the CSV, so drawn here as a variation of the CSV upload.
  • Copy the targets from another assembly — details above.
  • Export targets.

Possible, one day: import targets or respondents from non-tabular data (such as a JSON upload), or set them through a REST API. Left out of the charts so they stay about what exists or is on the way.

Glossary

Data source
Where an assembly's respondents come from, as chosen on the Data tab: Google Sheets, or the OpenDLP database (filled by CSV upload, registration page, or both). It never means where a target's percentages come from.
Respondent
Anyone in an assembly's data, whatever their status: in the pool, selected, or confirmed.
Target
One thing the selection balances on, such as Gender or Age. Each has values (Woman, 18–24 ...), and each value has the numbers: a percentage, and a min and max to select.
Tab
One tab inside a Google Sheets spreadsheet. The code sometimes calls it a worksheet.
Erasure
When someone asks for their details to be deleted, every copy has to be found and blanked. On the database paths OpenDLP blanks the respondent's row; any exported copies are the organiser's to deal with. On path 0 the spreadsheet is the only copy.
