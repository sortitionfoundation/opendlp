Workflow: cloning a project

Cloning makes a copy of an existing project, for demos and training. You choose which parts come with it. This page shows what can and can't be copied, which choices fit together, and what is different about the copy.

The copy is a separate project. Once it is made, editing or deleting either the original or the copy never touches the other. Nothing in the copy points back at the original.

Only projects held in OpenDLP can be cloned. A project whose data source is Google Sheets is refused.

An admin does it, for now. Cloning is a command an admin runs on the server; there is no button for it in the app yet. If you want a project cloned, ask an admin and tell them which parts you want — see asking for a clone.

Why some parts are never copied
  • Selection history. The copy hasn't run any selections. Its history starts empty.
  • Record of emails sent. It records real emails sent to real people from the original. It says nothing true about the copy.
  • Google Sheets export settings. If the original sends its respondents to a spreadsheet automatically, copying that would send the copy's demo respondents into the original's real spreadsheet.
  • Reply-to name and email, on the project and on each of its emails. Left blank so that emails sent from a demo never invite replies to the real organiser.
  • Comments on respondents. They are history about the original's selections.
  • Deleted respondents. All that is left of a deleted respondent is an empty row, kept so the original's records still make sense after their details were removed. The copy has no such records.

Which choices fit together

Some parts only work alongside others, so some choices are refused. The rules come from how the parts depend on each other:

  • A registration page needs its registration questions. The page is built from the questions; without them it would accept answers that fit nowhere.
  • Respondents need the registration questions. A respondent's answers are filed under the questions, and the respondent screens use the questions to show them.
  • Computed questions need both the targets and the registration questions. A computed question works out a target's value from another question's answer, so it is no use without either. If either is left out, computed questions are quietly dropped — this is never refused.

  • An active admin. The clone is made in the name of an admin, who must be named and must have an active account. That admin becomes the copy's creator and its Project Manager.
  • Held in OpenDLP. A project with Google Sheets as its data source is refused — its respondents and targets live in the spreadsheet, not in OpenDLP, so there is nothing here to copy. A project that hasn't chosen a data source yet can be cloned.
  • Archived projects can be cloned. The copy is always active.
  • No check on publishing. It doesn't matter whether the original's registration page was ever published.

Choosing the title

A new project's title may not be the same as the title of another project you can see that is not archived. Capital letters and spaces at either end don't count, so “Climate Assembly” and “climate assembly ” are the same title. This rule applies when creating or renaming a project too, not just when cloning.

The admin running the clone can see every project, so in practice the title is checked against every project that isn't archived. The “(copy)” ending is always in English.

Copying respondents

Respondents are the one part of a project that can hold real people's details. Copying them makes a second copy that would have to be found and blanked if someone asked for their details to be deleted. So it is never the default, and it takes two deliberate steps:

  1. Asking for respondents is refused unless you also state that the project is for training or a demo — that the respondents hold no real personal data.
  2. Then a confirmation on screen names how many will be copied: “This will copy 412 respondents. Confirm they contain no real personal data”. Answering no cancels the clone. (A script can skip this question.)

Each respondent copied:

  • keeps their answers, email and other details;
  • loses their answers to computed questions if those weren't copied (see which choices fit together), so the copy looks like a project that never had them;
  • is linked to the copy of the registration page they came through, or to no page if the pages weren't copied;
  • has no comments and no selection history.

Respondent status

By default everyone goes back into the pool, as if nothing had happened to them yet. The copy is a starting point for a demo, and has no selection history to explain why anyone would be selected or confirmed. If the demo needs to start part way through — to show replacements or confirmation calls, say — you can ask to keep the respondents' statuses instead. Asking to keep statuses without copying respondents is refused.

Team members

Only copied if you ask. Everyone on the original's team gets the same role on the copy. The admin who runs the clone is always the copy's Project Manager, even if they had a different role on the original.

What is different about the copy

Even the parts that are copied can't all be copied exactly. These things change:

        P4["Reply-to name and<br/>email left blank"]:::always

    subgraph PAGES["Registration pages"]
        direction TB
        R1["Always in test,<br/>never published"]:::on
        R2["New web addresses<br/>and short codes"]:::on
        R3["Images and documents<br/>point at the copy's own"]:::on
        R4["Activity log starts afresh:<br/>#quot;cloned from ...#quot;"]:::on
        R5["Emails keep their wording,<br/>reply-to left blank"]:::on
    end
  • Always in test. Copying a published page would put a second live registration page on the internet without anyone pressing publish. A test page also keeps its web address editable. If the demo needs a published page, publish the copy's page in the usual way.
  • New web addresses. Every registration page needs its own web address and short code, so the copy's are made fresh from its new title. The admin gets a list of the new addresses when the clone finishes.
  • Images and documents. The copy gets its own copy of every image and document, and its pages and emails are changed to use them. So the copy keeps working even if the original is deleted.
  • Activity log. The original's log names people who never touched the copy, so it isn't copied. The copy's log starts with one entry saying where it was cloned from.
  • “Registration page needs updating”. If the original's page was behind its questions, so is the copy's; if it was up to date, so is the copy's.

Asking for a clone

When you ask an admin for a clone, tell them:

  • which project to copy (its web address in the backoffice is enough);
  • the title you want, if not “… (copy)”;
  • which of the targets, registration questions and registration pages to leave out, if any;
  • whether to copy the respondents — and if so, that they hold no real personal data, and whether to keep their statuses;
  • whether to copy the team members.
For the admin running it

opendlp projects list finds the project's ID. Then:

opendlp projects clone PROJECT_ID --user-email admin@example.com [--title "..."] [--no-targets] [--no-questions] [--no-registration] [--respondents --for-training-or-demo] [--preserve-respondent-status] [--team] [--yes]

See docs/cli.md for the details.

Glossary

Project
What an organiser sets up in OpenDLP to find the people for one event: its data, targets, registration page, team and selections.
Data source
Where a project's targets and respondents are managed: in OpenDLP or in Google Sheets. Only projects managed in OpenDLP can be cloned.
Computed question
A registration question nobody answers: its value is worked out from another question's answer, such as an age range from a date of birth, so that it can be matched to a target.
Respondent
Anyone in a project's data, whatever their status: in the pool, selected, or confirmed.
Team member
A user with a role on a project, such as Project Manager or Confirmation Caller.
