Workflow: setting up targets, then registration fields

Two set-up jobs, done in order. First you build the selection targets — the demographic categories and how many of each you want — without thinking about the registration form at all. Then you build the registration fields, and make sure that between them they can supply the data every target needs.

Targets and registration fields are independent structures. A target does not name a field, and a field does not name a target. They meet in one place only: the check that asks “can every target get its value from the data this form collects?” — either from a field whose name and options match the target, or from a derived field that computes it.

That is why targets come first. You agree the categories with the client in target-shaped language, and only afterwards work out what to ask people on the form.

Add a target, then its values

A target is a category you want to stratify on: gender, age_bracket, region. A target value is one of the buckets inside it: Male, Female, Non-binary.

This is the whole minimum. A target with values, and nothing else filled in, is a valid target — the percentages, min/max, URL and comments can all wait.

Percentages, and how min and max are calculated from them

For each target value you enter the percentage of the assembly that should fall in that bucket. From the percentage and the already-agreed number-to-select, the min and max are calculated automatically:

  • min = floor(percentage × number-to-select)
  • max = ceil(percentage × number-to-select)

Because both are derived, changing the percentage or changing the number-to-select will move the min and max for every value that still has its auto-calculate link intact.

The percentages for a single target should add up to about 100.0. If they don't, a warning is shown — but it is only a warning. Rounding in published statistics means the total is often 99.9 or 100.1, and there are legitimate reasons for a bigger gap, so this never blocks you.

Setting min and max by hand — and breaking the link

You can type a min and max directly onto a target value instead of letting them be calculated. Doing so permanently breaks the auto-calculate link for that value: from then on, editing the percentage or the number-to-select will not touch its min and max.

The link is per target value, not per target — one hand-set value in a target does not detach the others.

This is exactly why target values carry their own comment field. A hand-set min/max is a decision someone made for a reason, and six weeks later nobody remembers the reason. Write it down next to the number.

Source URL and comments on the target

The target itself carries two pieces of provenance:

  • Source URL — where the percentages came from, typically a census table or an ONS page.
  • Comment — free text, generally about the source: which year, which geography, what was adjusted and why.
Deleting a target or a target value
  • Delete a target value — removes that one bucket, its percentage, min/max and comment.
  • Delete a target — removes the whole category: every value under it, plus the target's comment and source URL.
The “check the targets” button

A single button that runs the sanity checks that are possible at that moment. Which ones can run depends on what else exists yet:

  • Against number-to-select — always possible. Do the minimums sum to more than the number of seats? Do the maximums sum to fewer? Either makes the selection impossible before it starts.
  • Against the registration fields — only once fields exist. This is the same coverage check described in flow 2, run from the targets side.
  • Against the pool of respondents — only once people have registered. Are there actually enough people in each bucket to hit the minimum?

Because targets are set up before either fields or respondents exist, the first run of this button will usually only be able to do the first check. That's expected — it is a button you come back to.

Sections

A section has a name and nothing else. It groups fields on the registration page and gives the respondent a heading — Eligibility, Contact details, About you, Consent are the usual four.

Sections can be reordered and deleted. There is an unresolved question about what deleting a section does to the fields inside it — see open questions.

Moving and reordering fields

Two separate operations: reordering fields within a section, and moving a field between sections. Neither changes the field itself — this is purely about how the form reads to the person filling it in.

Copying fields from another assembly

Assemblies repeat. Rather than rebuild a near-identical set of sections and fields, copy them from an assembly you have already run and edit the differences.

Note that a copied derived field carries assumptions with it: an age-brackets field brings its boundaries, a postcode mapping brings its uploaded CSV. Those may not match this assembly's targets, so the coverage check matters more after a copy, not less.

The coverage check — does every target have data?

This is the single point where the two independent structures are compared. For each target, it asks whether the registration fields can produce a value for it. There are exactly two ways they can:

  1. Directly — there is a field whose name matches the target's name and whose options match the target's values. A gender field offering Male / Female / Non-binary satisfies a gender target with those three values.
  2. Via a derived field — a calculated field named after the target computes the value from one or more real form fields. Date of birth becomes age_bracket; postcode becomes region.

If neither exists for some target, the check reports it. Whether this is a button you press or something that runs automatically on every save is still open — the diagram draws it as a gate, which is true either way.

Generating the registration form

Once the fields are set, the registration form can be generated and served as the public web page. Derived fields never appear on it — they are computed after submission, from the fields that do.

Checkbox — the only field that can be optional

Every other field type is required on the registration form. A checkbox is the one type where you choose: must the respondent tick it to submit, or is ticking it genuinely their choice?

  • Must tick — can_attend, eligible, consent. These gate submission.
  • Real choice — stay_on_db. Ticked or not, the form submits.
Choice of options — and the “auto” form type

Each option has its own text and, optionally, its own help text. The form type controls how it renders:

  • Auto (the default) — radio buttons, unless there are more than 10 options, in which case a dropdown.
  • Radio buttons — forced, however many options there are.
  • Select dropdown — forced, however few.

This is also the type that a map-more-to-fewer derived field reads from, and the type an exact copy from a target produces.

Text (numeric)

A text field constrained to numbers, with an optional minimum and maximum. Both are optional — leave them blank for an unbounded number.

Date — full date or year only

Used mainly for date of birth. You choose whether to ask for a full date or just a year, which matters: year-only is less intrusive to ask for, but gives an age that can be a year out.

The minimum defaults to 1900-01-01 and the maximum to the start of the current year, which between them reject the obvious typos.

A date field is the usual input for an age-ranges derived field.

Why derived fields exist at all

Because the best question to ask a respondent is often not the shape you want to stratify on. Three recurring cases:

  • The target is coarser than the honest question. The target is age_bracket (16–29, 30–44, …) but asking someone to self-select a bracket invites error; asking for date of birth does not.
  • The target is coarser than a respectful question. Political party targets might be Conservative, Labour, LibDem, Reform, Other, while the form lists every party, with the smaller ones mapping to Other. The same argument applies to ethnicity: people should be able to see themselves in the list even when the target buckets are broad.
  • The target isn't something a person knows about themselves. A region target with values North / South / East / West / Central London means nothing to most respondents. They know their address. You know which postcodes fall in which region.

In all three cases you set up the target first, in target language, and only later work out which real question can feed it.

Age ranges

Date-of-birth fields go on the registration form. When someone registers, the system calculates their age and drops them into a bucket.

The bucket boundaries come from four numbers:

InputDefault
Minimum age16
Age boundaries (comma separated)30,45,60
Maximum age100
Date to calculate age ontoday

Worked example: minimum 16, maximum 100, boundaries 22,30,55 gives four brackets:

  • 16–21
  • 22–29
  • 30–54
  • 55–99

There is a button to work out the minimum age and the boundaries from the target with the matching name, so you don't retype what you already entered on the targets side.

Date to calculate age on defaults to today, but for an assembly you usually want the age people will be at the event, not at registration — so this is often set to the first assembly date.

Map more options to fewer

For when the form offers plenty of options and the target has few. Ethnicity is the standard case: 10 options on the form, 4 target buckets.

  1. Early on, you created the target with its 4 values.
  2. Now you create the field that will be on the form — a choice of options field with 10 options.
  3. Then you create this derived field: pick the target it feeds, and pick the registration field it maps from.
  4. You get one dropdown per registration option; each dropdown lists the target values. Every option must be assigned.

When someone registers, the system looks their answer up in that saved table and sets the target value accordingly.

Note the ordering constraint: the field you map from has to exist before you can build the mapping, because you pick it from a list of existing “choice of options” fields.

Map postcode to value (large mappings)

For when the form has a free-text box and the target has a small set of values, with a big lookup table in between. Postcode to region is the standard case.

  1. Enter the target values (or copy them from the matching target).
  2. Name the registration field this is based on — defaults to postcode.
  3. Upload a CSV with two columns. Each row is one postcode and the value it maps to. There can be thousands of rows.

The column titles should match the field name and the target name — postcode and region in this example.

When someone registers, the system looks their postcode up in the saved table and sets the target value.

Worth checking against the data-retention rules. The project's GDPR position is that no long-term copies of uploaded files are kept. A postcode-to-region CSV is reference data rather than personal data, so it is probably fine to store — but it arrives through a file upload, which is exactly the path that rule is about. Worth a decision rather than an assumption.

Exact copy

The simplest route: the target's name and values become a choice of options field's name and options. Gender in, gender out.

What it cannot fill in is the human half — the question text the respondent reads, the help text, and whether it renders as radios or a dropdown. Those are still yours to write.

Open questions

Things the description above doesn't settle, drawn out here rather than quietly decided in a diagram.

  1. Maximum age. The age-range form is described in two places with two different lists — one has minimum age, boundaries and calculation date; the other adds a maximum age defaulting to 100. The diagrams show maximum age, because the worked example (16, 100, boundaries 22,30,55) needs it to produce a top bracket of 55–99. Confirm it belongs on the form.
  2. Coverage check: button or automatic? Drawn as a gate, which is true whether it's a button or runs on every save. A button is honest about cost and lets you work in a broken state; automatic means nobody forgets. The likely answer is both — run automatically and show a persistent warning banner, with a button for the fuller cross-check against respondents.
  3. Deleting a section that has fields in it. Does it delete the fields, refuse until the section is empty, or move them somewhere? Refusing is the safest and least surprising, but it makes tidying up tedious.
  4. Deleting a target that a derived field feeds. A derived field is named after a target and may have copied that target's options. Deleting the target leaves the field orphaned. Warn, block, or allow and let the coverage check complain?
  5. Ordering constraint on “map more to fewer”. You pick the field to map from out of a list of existing “choice of options” fields, so that field must be created first. Flow 6 partly solves this for age ranges by letting you create the date field inline; the same escape hatch may be worth having here.
  6. CSV validation on the postcode mapping. The column titles “should match” the field and target names. Is that enforced, or advisory? And what happens at registration when a postcode isn't in the table at all — reject the submission, or record an unmapped value?
  7. Percentage tolerance. “Close to 100.0” needs a number. Published statistics routinely total 99.9 or 100.1 through rounding, so the threshold has to allow that without waving through a genuine mistake.

Glossary

Target
A category the selection stratifies on — gender, age_bracket, region. Holds target values, an optional source URL and an optional comment.
Target value
One bucket within a target — Male, 16-29, North London. Holds a percentage, a min and a max, and an optional comment.
Number-to-select
How many people the assembly needs. Agreed before any of this, and the multiplier that turns percentages into a min and max.
Auto-calculate link
The live connection from a target value's percentage to its min and max. Intact by default; broken permanently for that value the moment you type a min or max by hand.
Section
A named group of fields. Becomes a heading on the registration page.
Field
One question on the registration form — or, for a calculated field, one value computed from the answers rather than asked for.
Derived (calculated) field
A field that never appears on the form. It takes one or more real fields and produces the value a target needs: date of birth to age_bracket, ten ethnicity options to four, postcode to region. See flow 4.
